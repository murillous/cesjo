# Modelo Físico do Banco de Dados

## 1. Estado e finalidade

Este documento contém a versão revisada do modelo físico. A baseline técnica adotada é PostgreSQL. Durante a consolidação, foram corrigidas incompatibilidades do modelo anterior com PostgreSQL:

- `AUTO_INCREMENT` substituído por colunas identity;
- `ENUM` de MySQL substituído por `VARCHAR` com `CHECK`;
- `ON UPDATE CURRENT_TIMESTAMP` removido;
- identificadores com acentos eliminados;
- alterações posteriores incorporadas à criação das tabelas;
- separação entre conta de acesso e beneficiário atendido;
- criação explícita da entrada na lista de espera.

## 2. Escopo executável inicial

O script abaixo cobre somente o núcleo necessário aos RF001 e RF002 e à autenticação futura por perfil. Ele não pretende materializar requisitos ainda insuficientemente detalhados.

```sql
CREATE TABLE contas_acesso (
    id_conta BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nome VARCHAR(150) NOT NULL,
    email VARCHAR(254) NOT NULL UNIQUE,
    senha_hash VARCHAR(255) NOT NULL,
    perfil VARCHAR(30) NOT NULL,
    CONSTRAINT ck_conta_perfil CHECK (
        perfil IN ('COORDENADOR', 'EQUIPE_TECNICA', 'ADMINISTRATIVO', 'CONSULTA')
    )
);

CREATE TABLE beneficiarios (
    id_beneficiario BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nome VARCHAR(150) NOT NULL,
    data_nascimento DATE NOT NULL,
    cpf VARCHAR(11),
    responsavel VARCHAR(150) NOT NULL,
    telefone VARCHAR(20) NOT NULL,
    tipo_deficiencia VARCHAR(20) NOT NULL,
    beneficiario_bpc BOOLEAN NOT NULL DEFAULT FALSE,
    inscrito_cadunico BOOLEAN NOT NULL DEFAULT FALSE,
    origem_encaminhamento VARCHAR(30) NOT NULL,
    laudo_medico_referencia VARCHAR(500) NOT NULL,
    comprovante_residencia_referencia VARCHAR(500) NOT NULL,
    id_conta_cadastro BIGINT NOT NULL,
    data_criacao TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    data_atualizacao TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_beneficiario_conta
        FOREIGN KEY (id_conta_cadastro) REFERENCES contas_acesso(id_conta),
    CONSTRAINT ck_beneficiario_tipo_deficiencia CHECK (
        tipo_deficiencia IN ('SENSORIAL', 'FISICA', 'TEA', 'INTELECTUAL', 'MULTIPLA', 'T21')
    ),
    CONSTRAINT ck_beneficiario_origem CHECK (
        origem_encaminhamento IN (
            'CRAS', 'CREAS', 'JUDICIARIO', 'SAUDE', 'EDUCACAO', 'DEMANDA_ESPONTANEA'
        )
    )
);

CREATE TABLE lista_espera (
    id_lista_espera BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    id_beneficiario BIGINT NOT NULL,
    data_entrada DATE NOT NULL,
    data_saida DATE,
    motivo_saida VARCHAR(255),
    observacao TEXT,
    id_conta_cadastro BIGINT NOT NULL,
    data_criacao TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_lista_beneficiario
        FOREIGN KEY (id_beneficiario) REFERENCES beneficiarios(id_beneficiario),
    CONSTRAINT fk_lista_conta
        FOREIGN KEY (id_conta_cadastro) REFERENCES contas_acesso(id_conta),
    CONSTRAINT ck_lista_datas CHECK (
        data_saida IS NULL OR data_saida >= data_entrada
    )
);

CREATE UNIQUE INDEX uk_lista_espera_beneficiario_ativo
    ON lista_espera (id_beneficiario)
    WHERE data_saida IS NULL;

CREATE INDEX ix_lista_espera_ordenacao
    ON lista_espera (data_entrada, id_lista_espera)
    WHERE data_saida IS NULL;
```

## 3. Decisões de modelagem

### 3.1 Conta de acesso e beneficiário

`contas_acesso` armazena somente profissionais autorizados. `beneficiarios` armazena pessoas candidatas ou atendidas. Isso elimina a antiga ambiguidade do termo `Usuario`.

### 3.2 Lista de espera

A lista é uma entidade própria. Uma pessoa pode ter histórico de várias entradas, mas o índice parcial impede duas entradas ativas simultâneas.

Uma entrada está ativa enquanto `data_saida` for nula. Não foi criado enum de status porque o requisito ainda não define estados e transições da fila.

### 3.3 Posição e prioridade

A posição não é persistida. Ela deve ser calculada a partir das entradas ativas.

O RF002 confirma a ordem cronológica, mas a combinação dessa ordem com a prioridade BPC + CadÚnico ainda precisa de validação do responsável pelo negócio. Por isso, o modelo armazena os indicadores necessários sem fixar silenciosamente o algoritmo.

### 3.4 Arquivos

O banco armazena apenas uma referência ao laudo e ao comprovante. O mecanismo de armazenamento, os formatos aceitos, o limite de tamanho, a autorização de download e a retenção ainda precisam ser definidos antes do RF001 ser considerado completo.

### 3.5 CPF e data de nascimento

- A data de nascimento é obrigatória para validar a faixa etária de 18 a 59 anos.
- O CPF permanece opcional e sem unicidade até confirmação do negócio.

## 4. Módulos ainda não materializados

As estruturas de vagas, visitas, escutas, PIA, vínculo com o serviço, desligamentos, violações, atividades, comunicações, gestão institucional, relatórios e auditoria só devem entrar em migrations depois que os pontos pendentes registrados na [matriz de rastreabilidade](matrizRastreabilidade.md) forem resolvidos.

## 5. Migrações

Quando a implementação começar, este SQL deve ser convertido na migration inicial da ferramenta escolhida pelo projeto. O Hibernate não deve criar ou atualizar o schema automaticamente.
